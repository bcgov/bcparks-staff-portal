You are an expert maintenance agent for this repository.

## Mission

- Make small, targeted changes that preserve existing behavior unless the user asks otherwise.
- Prefer the current project patterns over introducing new abstractions.
- Keep frontend and backend data contracts aligned.

## Working Rules

- Run the relevant project validation checks before finishing. Include linting and a focused test, build, or runtime check when available.
- Keep formatting consistent with existing tooling and avoid broad unrelated reformatting.
- Check for an existing helper, component, or project pattern before adding a new abstraction.
- Add concise JSDoc to new functions and modified non-trivial functions when their parameters or return values are not obvious.

### API and data integrity

- Do not change API response shapes unless requested.
- When changing season or date logic, verify all routes, jobs, import/sync code, and frontend consumers that use it.
- Treat date boundaries carefully (string vs `Date` behavior, timezone assumptions, null/empty semantics).

### Migrations and schema

- Ask first before creating/editing migrations, destructive data updates, or reseeding strategy changes.
- Never manually edit previously applied migration intent without explicit instruction.

### Frontend changes

- Reuse existing components and styles where possible.
- Keep forms/tables behavior stable; avoid introducing duplicate sources of truth for derived fields.
- Respect current visual system and avoid broad style rewrites unless requested.

### Security and secrets

- Never commit secrets, tokens, or real credentials.
- Do not print `.env` values in logs, patches, or summaries.
- `psql` is only for the local dev database.
- Never access OpenShift in any way: no `oc`, `kubectl` or `helm`, no port-forwards or tunnels, and no triggering deploy workflows.
- If a task needs OpenShift, give the developer the commands to run. Start with `oc login` and `oc project`, keep each step short, and explain what it does.

### Commits and pull requests

- Write commit messages and PR descriptions about the change itself: what changed and why.
- Don't include tool or vendor names, "generated by" notes, or `Co-authored-by` trailers for tools.
- Never commit or push to `main`, `alpha` or `staging/*`. Do all work on a feature branch.
- Only push or force-push when the developer explicitly asks for that push. Approval for an earlier push doesn't carry over.
- Never amend, squash, rebase or otherwise rewrite commits unless the developer asks or confirms first. Make a new commit instead.
- Never create or edit PRs (no `gh pr create` or `gh pr edit`). Write the PR title and description as text, using `.github/pull_request_template.md`, and the developer will create the PR in GitHub. Put the ticket number under Jira Ticket (`None` for `NOBUG` work).

### Working with Jira

- The team tracks work in Jira, in the `CMS` project.
- Name feature branches after the ticket, e.g. `CMS-123`.
- For later work on the same ticket (QA fixes, bug fixes, or splitting work into stacked PRs), add a short lowercase kebab-case suffix, e.g. `CMS-123-qa-fixes` or `CMS-123-content-changes`. Remote branches are deleted when their PR is merged, so don't reuse a merged branch name.
- Start PR titles and commit messages with the ticket number, e.g. `CMS-123: Short description`. Commit messages are a single line with no body, 72 characters or less including the ticket number, so GitHub doesn't cut it off when it fills in the PR title. Put the details in the PR description.
- For work without a ticket, use `NOBUG` instead, e.g. branch `NOBUG-short-description` and title `NOBUG: Short description`. Don't use placeholder tickets like `CMS-000` or `CMS-00`, even though they appear in older history.

## Dev Container Environment

- Agents run inside the `frontend` or `backend` dev container (see `docker-compose.dev.yml`). Both mount the repo at `/app`.
- The Postgres dev database is `db:5432`. `psql` is installed only in the backend container: `psql -h db -U user mydatabase` (dev credentials are in `docker-compose.dev.yml`).
- The backend API is `backend:8100`. It isn't started automatically; run `npm run dev` in the backend container.
- `POSTGRES_*` env vars exist only in the backend container. From the frontend container, `cd /app/backend && npm test` still works for tests that don't need the database.
- There is no docker CLI inside the containers, so you can't `docker exec` into another container.
- `gh` is available in both containers. `/home/node` is a persisted volume (`dev-home`), so `gh auth login` and other CLI logins survive rebuilds.
- Validation: `npm run lint` and `npm test` in `frontend/` or `backend/`.

## Delivery Checklist

- Identify smallest possible file set.
- Implement minimal patch.
- Run relevant validation for the touched area.
- Summarize what changed, why, and any residual risk.

## Boundaries

- Always: Keep edits focused, preserve conventions, validate impacted code paths.
- Ask first: New dependencies, migration/schema changes, CI/CD or container config changes, large refactors.
- Never: Edit vendored dependencies, commit secrets, use destructive git operations without explicit request, or access OpenShift.
